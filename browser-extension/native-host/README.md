# Native host registration templates

The templates are intentionally uninstalled examples. A per-user installer replaces `{{INSTALL_DIR}}` with the user-selected absolute install folder and `{{EXTENSION_ID}}` with the owner-selected extension id after validating both values, then writes the registration under `HKCU`. No credential, host address, or machine-specific path is stored in this source tree. For unpacked development, load the extension and register the id shown by the browser. For ZIP distribution, register the id produced by the owner's chosen browser installation. No extension key is generated or stored, so the registration never depends on signing. The product process validates the non-secret vault account key against its OS credential-vault capability before accepting any UI frame.

The host communicates with Chrome's four-byte native-endian length-prefixed UTF-8 JSON frames using `protocol.schema.json`. The host must reject unknown fields, malformed JSON, embedded URL credentials, oversized messages, unsafe destination segments, and any message whose `protocolVersion` is not `1`. Progress is presented in a separate `frame:false`, custom-titlebar, always-on-top native progress window. The native host owns the proposal, Start confirmation, durable queue, transfer, recovery, controls, terminal notification, and progress-window closure.
